## 上云前提
1. 用户明确同意持续收费与数据存储区域后，开通**持久化**的正式数据库；禁止用 Render 30 天后到期的 Free PostgreSQL 保存正式账目。
2. 现有每台手机／平板／电脑数据独立，云迁移前逐一导出只读 JSON 快照。对每个账本计算 SHA256，登记导入批次与订单来源设备。
3. 初始迁移需提供预览：本机订单数、库存数量、正在使用房间，与云端导入前状态对比；不得默认覆盖任一端。
4. 相同 `order.id` 导入必须幂等，冲突进入人工审核队列；不静默覆盖云端数据或房间状态。
5. 保留旧键、旧版本只读备份至少到用户正式确认迁移验证完成并且恢复演练成功；迁移结束也不应自动删除原始数据。

## 数据架构
- PostgreSQL：tables `events` (append-only audit), `orders` (status active/voided), `sessions`, `rooms`, `products`, `inventory`, `stock_movements`, `purchases`, `income_adjustments`, `expenses`, `import_batches`, `backup_jobs`.
- 所有增删改使用服务端事务、稳定 UUID、request idempotency key、schemaVersion、`row_version`、`created_at`/`updated_at`。
- 不得硬删除营业订单及其出入库明细；修改和作废要留下操作人、时间、修改原因、前后值。
- 库存冲正要根据实际退货判定，避免仅因财务作废就错误返库。
- 财务口径：报表展示系统应收、实际收款、人工调整、非进货支出和 **暂估利润（未计存货成本、税费和未录费用）**。
- 变更数据库字段只允许增量迁移、版本化 migration；发布前在备份副本回归测试。

## 多设备实时 / 离线
- 在线：服务端数据库作为唯一权威账本；消息流（SSE 或轮询）推送房态、订单、库存版本至所有已授权设备。
- 离线：设备本地持久队列先记带唯一 operation id 的操作；联网后按序重放，服务端事务去重、返回版本。
- **同一房间同时在两台离线设备改动**时，不能“最后保存的人覆盖前一个”。返回冲突、显示人工审核，原操作完整保留直到处理完成。
- 确认队列全部同步及快照一致后才显示“已同步”；禁止只根据 `navigator.onLine` 宣称同步成功。
- 多用户管理员／收银员分别授权，云端 API 也实施权限控制而非仅屏蔽按钮。
